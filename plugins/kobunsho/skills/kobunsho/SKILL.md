# 公用文の書き方（開発文書）

日本語の開発文書を、「公用文作成の考え方」（令和4年1月7日 文化審議会建議。以下「建議」という。）に沿って書くための規則である。表記の細目は `references/hyoki.md` にまとめた。

## 適用の範囲

開発文書は、建議の分類では「記録・公開資料等」に当たるものとして扱う。公用文表記の原則に従い、読み手である開発者に合わせて書き方を工夫する。

次の順に従う。

1. プロジェクトの `CLAUDE.md` や規定文書が定める文書種別・表記
2. このスキルの規則
3. 判断がつかない場合は建議の原則

次のものには適用せず、元の表記のまま残す。

- コード、コマンド、識別子、ファイル名、URL
- ログやエラーメッセージの実物、引用
- 固有名詞（製品名、サービス名、人名）
- 画面の文言のように、表記が外部で決まっているもの

## 文体

- 常体（である体）で書き、一つの文書の中で敬体と混ぜない。敬体で書かれた文書を直す場合は、敬体のまま直す。
- 常体は「である・であろう・であった」を使う。「だ・だろう・だった」は使わない。
- 文語の名残を使わない。
  - のごとく → のように
  - 進まんとする → 進もうとする
  - 大いなる → 大きな
  - 〜しつつ → 〜しながら
- 「べく」「べし」は使わない。「するべき」ではなく「すべき」と書き、文末は「すべきである」「すべきもの」とする。

## 文書の組み立て

- 結論を最初に書き、理由や詳細を後に続ける。作業報告やプルリクエストの本文は、冒頭で結論を示す。
- 標題には、主題と文書の性格（報告、提案、依頼、確認など）を入れる。「〜について」で終わらせない。
  - ログ出力について → ログ出力の形式を JSON に変える提案
- 見出しだけを追えば内容がつかめるようにする。見出しは内容の中心を短く示す。
- 分量の上限を決めてから書き、必要性の低い情報は削る。副次的な情報は別の文書に分ける。
- 読み手がする必要のないことも明示すると、迷わせずに済む（例：「上記に該当しない場合、作業は不要である。」）。

## 文の書き方

- 一文を短くし、論点を一つにする。50〜60字を超えたら、分けられないか見直す。
- 三つ以上を並べるときは箇条書にする。
- 主語と述語を対応させる。文の途中で主語を変えない。
- 接続助詞の「が」や中止法（「〜し、〜し、」）で文をつなぎ続けない。
- 同じ助詞を続けない。
  - 本年の当課の取組の中心は → 本年、当課が中心的に取り組んでいるのは
- 受身形をむやみに使わない。誰が行ったかが分かるように書く。
- 二重否定を使わない。
  - …しないわけではない → …することもある
  - ○○を除いて、実現していない → ○○のみ、実現した
- 係る語と受ける語、指示語と指す内容を近くに置く。複数の意味に取れる書き方をしない。
- 読点の位置で意味が変わる場合は、文を書き換える。
- 複数の修飾節が掛かるときは、長いものから先に置くか、文を分ける。

## 言葉の選び方

- 程度や時期をぼかさず、数値や日付で書く。期間は起点と終点を示す。
  - 幾つか指摘する → 3点指摘する
  - 早めに → 5月14日正午までに
- 境界を示す言葉は、起点を含むかどうかで使い分ける。
  - 以上・以下・以前・以後は、起点を含む（100件以上 = 100件を含む）
  - 超える・未満は、起点を含まない（100件を超える = 100件を含まない）
- 「等」「など」は、示すべきものを全て挙げられるなら使わない。使う場合は、前に代表的なものを置く。
- 「から」は起点、「より」は比較に使う。起点に「より」を使わない。
  - 長官より説明がある → 長官から説明がある
- 回りくどい言い方を削る。
  - 利用することができる → 利用できる
  - 調査を実施した → 調査した
  - 問題があるということになる → 問題がある
- 意味の重なる言い方（重言）を使わない。
  - 各都道府県ごとに → 都道府県ごとに
  - 約20名くらい → 約20名
  - まず最初に → 最初に
- 外来語と専門用語は、読み手に通じるかで判断する。
  - 開発者に定着した技術用語（コミット、デプロイ、プルリクエスト）は、そのまま使う。
  - 定着していない外来語は、日本語に言い換える（アジェンダ → 議題）。
  - 言い換えられない語は、説明を添える。
- 読み手が知らないおそれのある略語は、初出で元の語を示す。
  - 受け入れテスト（以下「UAT」という。）
- 及び・並びに・又は・若しくは は、法令と同じ意味で使う。結び付きが二段以上になる場合は、箇条書に分ける。
- 「〜のメッカ」のような、特定の宗教や職業、性別に関わるたとえを使わない。

## 表記

lint（`textlint`）で機械的に拾えるものが多い。細目は `references/hyoki.md` を読む。

- 漢字は、常用漢字表の字種・音訓の範囲で使う。表にない漢字・音訓を含む語は、仮名にするか言い換える。
  - 紐付け → ひも付け、齟齬 → 食い違い、揃える → そろえる、雛形 → ひな形
  - 字体は、常用漢字表の通用字体を使う（補塡、頰、剝離）。
- 次の語は仮名で書く。
  - 形式名詞：こと、とき、ところ、もの、ため、とおり、よう、わけ、うち、ゆえ（具体的な対象を指す場合は漢字）
  - 補助動詞：〜ていく、〜ていただく、〜てください、〜てくる、〜てみる、〜てほしい、〜てよい
  - 動詞・形容詞：いる、できる、ある、ない（「出来が良い」「有り・無し」などは漢字）
  - 接続詞：したがって、ただし、また、なお、さらに、しかし、そして、ところが
  - 助詞：など、くらい、ほど
- 次の語は漢字で書く。
  - 接続詞：及び、又は、並びに、若しくは
  - 副詞：既に、直ちに、更に、必ず、少し、全て
  - 接頭辞：御（御確認、御意見）。ただし表外漢字を含む語は仮名（ごちそう）
- 送り仮名は「送り仮名の付け方」の本則に従う（行う、終わる、表す）。活用のない複合名詞のうち、公用文で送り仮名を省くと定められた語は省く（手続、取扱い、打合せ、問合せ、申込み、届出、見積り、引継ぎ、取消し、締切り）。動詞は省かない（問い合わせる、引き継ぐ）。
- 外来語は、長音符号を付けて書く（サーバー、ユーザー、フォルダー、パラメーター）。「リポジトリ」「ディレクトリ」のような -ry、-ty で終わる語も原則は長音符号を付けるが、プロジェクトの表記が決まっていればそれに従う。「ヴ」は使わず、バ行で書く。
- 数字は、算用数字を半角で書く。
  - 四桁以上は三桁ごとにコンマで区切る（5,000）。兆・億・万は漢字で書く（5億3,000万）。
  - 概数、成語、「一つ」「一人」のような数え方は漢数字で書く（数十件、二者択一、一つ）。
  - 「3か所」「7か月」と書く。「ヶ」「カ」は使わない。
- 符号の使い方
  - 句点は「。」、読点は「、」を使う。
  - 括弧は（）と「」を基本とし、入れ子でもそのまま重ねる。
  - 括弧の中で文が終わる場合は、閉じ括弧の前に句点を打つ（以下「基本計画」という。）。語句で終わる場合は打たない。
  - 「？」「！」は使わない。
  - 繰り返し符号は「々」だけを使い、漢字1字の繰り返しに限る（一人一人、ますます）。
  - 矢印や箇条書の記号は、文書の中で使い方を統一する。
- Markdown の書き方
  - 段落の冒頭を1字下げしない。段落の間を空けて区切る。
  - 階層は見出しで示し、「第1」「（1）」のような項目番号は必要な場合だけ付ける。

## 書いたあとの確認

1. プロジェクトに textlint が入っていれば、kobunsho の hook が、書き換えた範囲の指摘を返す。エラーは直す。「【kobunsho:要確認】」の警告は文脈で判断し、漢字のままが正しければ直さない。
2. 規定文書や長い文書は、kobunsho-reviewer エージェントに読ませる。lint で拾えない文の書き方を確かめるためである。
3. 既存の文書を直すときは、頼まれた範囲の外の表記まで直さない。表記の揺れに気づいたら、別の作業として報告する。
